# Техническое задание: CRM для продажи косметики

## 1. Назначение системы

CRM предназначена для небольшой компании, которая производит и продает косметику, вручную создает заказы, ведет клиентов, товары, партии, складские остатки, напоминания и аналитику продаж.

Система должна работать как веб-приложение, адаптированное под desktop и мобильные устройства, включая iPhone 12 mini.

## 2. Рекомендуемая архитектура

### 2.1. Общий подход

Рекомендуется модульный монолит:

- один frontend;
- один backend;
- одна PostgreSQL база данных;
- разделение backend-кода по доменным модулям.

Такой подход проще в разработке, дешевле в поддержке и достаточен для текущего масштаба CRM.

### 2.2. Рекомендуемый стек

Frontend:

- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query;
- Zustand или Redux Toolkit для локального состояния;
- UI-библиотека: shadcn/ui, Mantine или Ant Design;
- адаптивная верстка под desktop и mobile.

Backend:

- NestJS;
- TypeScript;
- PostgreSQL;
- Prisma ORM;
- JWT access/refresh tokens;
- bcrypt/argon2 для паролей;
- Docker Compose для локального и production-запуска.

Инфраструктура:

- nginx как reverse proxy;
- backend API;
- frontend SPA;
- PostgreSQL;
- регулярные backup базы данных.

## 3. Роли и доступы

В системе должны быть роли:

- `SUPER_ADMIN`;
- `MANAGER`.

Самостоятельная регистрация пользователей запрещена.

Первый `SUPER_ADMIN` создается через seed-скрипт или CLI-команду при установке системы.

`SUPER_ADMIN` может:

- создавать менеджеров;
- редактировать пользователей;
- блокировать пользователей;
- видеть все разделы системы;
- выполнять все действия менеджера.

`MANAGER` может:

- создавать и редактировать клиентов;
- создавать и редактировать товары;
- создавать и редактировать партии;
- создавать заказы;
- менять статусы заказов;
- создавать напоминания;
- добавлять расходы;
- смотреть аналитику.

Права на просмотр финансовой аналитики одинаковые для `SUPER_ADMIN` и `MANAGER`.

## 4. Авторизация

Вход осуществляется по логину и паролю.

Требования:

- страница входа;
- защита всех внутренних страниц;
- хранение паролей только в виде хэша;
- refresh/access token авторизация;
- возможность деактивировать пользователя.

Главное меню:

## 6. Главная страница

Главная страница должна отображать:

- текущую дату и время;
- выручку за текущий день;
- выручку за текущий месяц;
- список заказов, ожидающих сборки и отправки;
- список напоминаний на текущую дату;
- кнопку создания заказа;
- кнопку создания напоминания.

Приоритет отображения заказов:

1. `ON_ASSEMBLY`;
2. `AWAITING_PAYMENT`;
3. `CLOSED`;
4. `RETURNED`;
5. `CANCELLED`.

## 7. Заказы

### 7.1. Статусы заказов

Заказ должен иметь один из статусов:

- `ON_ASSEMBLY` - на сборке;
- `AWAITING_PAYMENT` - ожидает оплаты;
- `CLOSED` - закрытый, оплачен;
- `RETURNED` - возврат;
- `CANCELLED` - отменен.

Цвета статусов:

- `ON_ASSEMBLY` - желтый;
- `AWAITING_PAYMENT` - зеленый;
- `CLOSED` - голубой;
- `RETURNED` - красный;
- `CANCELLED` - серый.

### 7.2. Жизненный цикл заказа

Новый заказ создается в статусе `ON_ASSEMBLY`.

Допустимые переходы:

- `ON_ASSEMBLY` -> `AWAITING_PAYMENT`, действие "Отправлен";
- `AWAITING_PAYMENT` -> `CLOSED`, действие "Оплачен";
- `AWAITING_PAYMENT` -> `RETURNED`, действие "Возврат";
- `ON_ASSEMBLY` -> `CANCELLED`, действие "Отменить";
- `AWAITING_PAYMENT` -> `CANCELLED`, действие "Отменить".

Повторно открыть или переотправить заказ в статусе `RETURNED` нельзя. Для повторной продажи создается новый заказ.

### 7.3. Информация в заказе

Заказ должен содержать:

- клиента;
- ФИО покупателя;
- телефон;
- город;
- адрес;
- сервис доставки;
- стоимость доставки;
- способ оплаты;
- скидку;
- список товаров;
- сумму товаров;
- сумму скидки;
- итоговую сумму товаров после скидки;
- сумму доставки;
- итог к оплате;
- статус;
- дату создания;
- дату отправки;
- дату оплаты;
- дату возврата;
- комментарий менеджера.

Сервисы доставки:

- Белпочта;
- Европочта;
- СДЭК;
- Автолайт;
- Самовывоз.

Способы оплаты:

- наложенный платеж;
- наличный платеж;
- безналичный платеж.

Интеграции с сервисами доставки не требуются.

### 7.4. Создание заказа

Форма создания заказа должна включать:

- поиск клиента по базе;
- создание нового клиента, если его нет;
- автозаполнение полей клиента из карточки;
- выбор товаров;
- создание нового товара при необходимости;
- выбор партии товара;
- количество товара;
- автоматическое подтягивание цены товара;
- применение персональной скидки клиента;
- ручное изменение скидки для заказа;
- расчет итогов.

Скидка применяется только к сумме товаров без учета доставки.

### 7.5. Учет остатков

Остатки товара учитываются по партиям.

При создании заказа остатки не списываются.

Остатки списываются только при переходе заказа:

`ON_ASSEMBLY` -> `AWAITING_PAYMENT`.

Если товара на складе меньше, чем указано в заказе, это не должно блокировать создание заказа. При отправке система должна показать предупреждение о недостатке остатка. Допускается отрицательный остаток партии.

### 7.6. Возврат

При переходе заказа в статус `RETURNED` менеджер выбирает действие по товарам:

- вернуть на склад;
- списать.

Если выбрано "вернуть на склад":

- товары возвращаются в те же партии, из которых были списаны.

Если выбрано "списать":

- остатки не возвращаются.

При возврате:

- клиент автоматически получает признак черного списка;
- заказ исключается из прибыли и выручки;
- заказ учитывается в количестве возвратов;
- дата учета возврата в аналитике определяется датой создания заказа;
- расходы по возврату менеджер добавляет вручную в месячные расходы.

Отдельная аналитика списаний не требуется.

### 7.7. Страница заказов

Страница должна содержать:

- список заказов;
- поиск по фамилии клиента;
- фильтр по статусу;
- фильтр по месяцу создания;
- кнопку создания нового заказа;
- карточку/таблицу заказа;
- быстрые действия по статусам;
- просмотр состава заказа.

Если сортировка не задана, заказы отображаются по приоритету:

1. `ON_ASSEMBLY`;
2. `AWAITING_PAYMENT`;
3. `CLOSED`;
4. `RETURNED`;
5. `CANCELLED`.

## 9. Продукты и партии

### 9.1. Основная модель

В системе нужно разделять:

- продукт;
- партию продукта.

Продукт отвечает за общее наименование.

Партия отвечает за конкретный выпуск, остаток, себестоимость и срок годности.

В аналитике партии не должны отображаться как отдельные категории. Товар с одним названием, но разными партиями считается одним товаром.

Агрегация в аналитике выполняется только по названию товара.

### 9.2. Продукт

Продукт должен содержать:

- название;
- масса/объем;
- единица измерения: г, мл, кг, шт;
- цена продажи;
- аромат;
- цвет;
- описание;
- дату создания.

Обязательные поля:

- название;
- масса/объем;
- единица измерения;
- цена продажи.

### 9.3. Партия

Партия должна содержать:

- продукт;
- номер партии;
- количество на складе;
- себестоимость единицы;
- срок годности;
- дату производства, необязательно;
- комментарий.

Обязательные поля:

- продукт;
- номер партии;
- количество на складе;
- себестоимость;
- срок годности.

### 9.4. Страница продуктов

Страница должна содержать:

- количество всех наименований продуктов;
- список продуктов;
- поиск по названию;
- поиск по аромату;
- сортировку по сроку годности;
- сортировку по количеству;
- сортировку по популярности;
- сортировку по наименьшей прибыли;
- сортировку по наибольшей прибыли;
- кнопку добавления продукта.

### 9.5. Карточка продукта

Карточка продукта должна содержать:

- основные поля продукта;
- возможность редактирования;
- историю всех партий;
- список клиентов, которые покупали этот продукт;
- статистику продукта.

Статистика продукта:

- общее количество заказов;
- общая сумма продаж;
- количество заказов по месяцам;
- сумма продаж по месяцам;
- количество проданных единиц;
- прибыль по продукту.

Напоминания на текущую дату отображаются на главной странице.

## 11. Аналитика

### 11.1. Периоды

Аналитика должна поддерживать фильтры:

- текущий месяц;
- выбранный месяц;
- год.

### 11.2. Учет заказов

В выручке и прибыли учитываются заказы со статусами:

- `ON_ASSEMBLY`;
- `AWAITING_PAYMENT`;
- `CLOSED`.

Заказы со статусами `RETURNED` и `CANCELLED` не учитываются в выручке и прибыли.

Если заказ был возвращен, он исключается из прибыли.

Возвраты считаются по дате создания заказа.

### 11.3. Основные показатели

Аналитика должна показывать:

- количество заказов;
- количество возвратов;
- выручку по товарам;
- доставку, оплаченную клиентами;
- всего к оплате клиентами;
- средний чек;
- себестоимость проданных товаров;
- валовую прибыль;
- расходы месяца;
- чистую прибыль;
- количество новых клиентов;
- количество повторных заказов;
- продажи по продуктам.

### 11.4. Формулы

Выручка по товарам:

`сумма товаров после скидки по заказам ON_ASSEMBLY, AWAITING_PAYMENT, CLOSED`

Доставка:

`сумма доставки по заказам ON_ASSEMBLY, AWAITING_PAYMENT, CLOSED`

Всего к оплате клиентами:

`выручка по товарам + доставка`

Себестоимость:

`сумма costPriceSnapshot * quantity по позициям заказов ON_ASSEMBLY, AWAITING_PAYMENT, CLOSED`

Валовая прибыль:

`выручка по товарам - себестоимость`

Чистая прибыль:

`валовая прибыль - расходы месяца`

Средний чек:

`выручка по товарам / количество учитываемых заказов`

Повторный заказ:

`любой заказ клиента начиная со второго учитываемого заказа`

### 11.5. Расходы

Расходы вводятся вручную за месяц.

Расход должен содержать:

- месяц;
- год;
- категория;
- сумма;
- комментарий;
- дата создания;
- автор.

Примеры категорий:

- налог;
- аренда;
- коммунальные платежи;
- коробки;
- расходные материалы;
- доставка/возврат;
- прочее.

### 11.6. Аналитика по продуктам

Продукты в аналитике агрегируются только по названию.

Если один и тот же товар продавался из разных партий, в аналитике он отображается как один товар.

Для каждого товара показывать:

- название;
- проданное количество;
- сумма продаж;
- себестоимость;
- прибыль;
- количество заказов.

Прибыль по товару:

`сумма продаж товара - себестоимость проданных единиц товара`

## 15. Валидация и бизнес-правила

Обязательные проверки:

- пользователь не может войти, если деактивирован;
- менеджер не может самостоятельно зарегистрироваться;
- заказ не может быть создан без клиента;
- заказ не может быть создан без товаров;
- количество товара в заказе должно быть больше 0;
- скидка не может быть меньше 0;
- скидка не может быть больше 100%;
- стоимость доставки не может быть отрицательной;
- при отправке заказа списываются остатки по партиям;
- при возврате товары возвращаются в исходные партии, если выбран возврат на склад;
- при возврате клиент автоматически попадает в черный список;
- `RETURNED` и `CANCELLED` исключаются из выручки и прибыли.

## 16. MVP

Первая версия должна включать:

1. Авторизацию.
2. Роли `SUPER_ADMIN` и `MANAGER`.
3. Управление пользователями для `SUPER_ADMIN`.
4. Клиентов.
5. Продукты.
6. Партии.
7. Создание заказов.
8. Смену статусов заказов.
9. Списание остатков при отправке.
10. Возвраты с выбором "вернуть на склад" или "списать".
11. Напоминания.
12. Главную страницу.
13. Расходы за месяц.
14. Базовую аналитику.

## 17. Нефункциональные требования

- интерфейс должен корректно работать на iPhone 12 mini;
- все суммы хранятся в BYN;
- денежные значения хранить в копейках или decimal-типе без float;
- все даты хранить с timezone;
- действия изменения статуса заказа логировать;
- API должен возвращать понятные ошибки валидации;
- база данных должна регулярно архивироваться;
- удаление важных сущностей желательно делать мягким, через архивирование или деактивацию.
